# 赛豆企业知识平台产品使用手册 v4.0

这是一份由多位同事协同 Agent 编写、核对和维护的产品操作手册。Markdown 是正文源文件，截图随仓库保存；定稿后再生成 Word。

- 编写基线：《赛豆企业知识平台产品使用手册（v3.4）》（2026-09-29），原件不改动。
- 主要依据：测试环境中的实际操作（平台 v4.1.2，含 1030 / 1106 版本功能）；环境地址与账号通过团队内部渠道获取。
- 版本范围：标注【1130 版本】的小节可使用原型截图；没有原型且环境不能操作的内容先不补写。
- 当前状态：2026-11-26 完成全书复核；[待确认汇总](待确认汇总.md) 仍有待产品、研发或对应负责人确认的事项。

## 一、协作约定

### 人负责什么

每位负责人认领章节或小节，判断环境功能是否符合产品预期，处理本节的「待确认」，核对 Agent 修改的正文和截图，再通过 Pull Request 交付。涉及产品口径、发布范围、权限规则和审批结论的事项，由对应产品或研发确认，Agent 不代替人作决定。

### Agent 负责什么

Agent 可以读取旧手册与现有章节、到测试环境核对功能、截取操作界面、修改正文和图注、检查图片引用与编号，并记录变更和待确认事项。

每次任务限定在明确的小节和预期产出内。负责人先交代「改哪一节、依据什么、要补哪些图、什么操作不能做」，不要只给 Agent 一句「更新全书」。

### 提交前必须检查 CHANGELOG（强制）

这是硬性规则，Agent 和人一样遵守：**每次 `git commit` 之前，先确认本次改动已在 [CHANGELOG.md](CHANGELOG.md) 中登记**。

提交前按顺序执行：

```bash
git status --short
git diff --stat
```

然后打开 `CHANGELOG.md`，确认本次改动有一条对应记录，且包含修改内容、截图、验证范围、待确认事项和负责人。

再用下面的命令检查 CHANGELOG 是否在本次暂存改动中（有输出说明已包含；无输出说明漏记，先补写再提交）：

```bash
git diff --cached --name-only | grep -x 'CHANGELOG.md'
```

也可以一次检查工作区里是否改过 CHANGELOG：

```bash
git status --short CHANGELOG.md
```

**没有登记 CHANGELOG 的提交应当被退回。** 只修复空格、标点或图片压缩等不改变内容的格式调整可以不记录，但要在 PR 中说明原因。

### 环境与数据安全

- 测试环境地址、账号、口令和密钥不写入仓库，不提交到 GitHub。
- 新建测试数据统一使用「手册示例-」前缀。
- 不修改或删除他人已有数据，不向真实人员发送消息。
- 禁止执行列表级或批量的发布、删除、执行、同步、重跑、移交、归档、清空、授权提交，不点击「创建密钥」，不对他人对象执行发布或运行。
- 只允许对自己创建的「手册示例-」对象执行必要的提交类操作，并在操作前确认只选中了该对象。其他对象只打开查看和截图，随后取消。
- 审批类操作最多提交到「待审批」，不代替审批人通过或驳回。
- 菜单、路由、浏览器操作方法和完整安全红线见 [_ref/环境现状-菜单与路由.md](_ref/环境现状-菜单与路由.md)。该文件记录了历史误操作，所有操作环境的 Agent 必须先读。

## 二、开始一次任务

### 1. 领取任务

在分工表中填写负责人，或在 Issue / PR 标题中注明章节与小节。同一小节同一时间只由一位负责人修改；大章可以按不重叠的小节拆分。

推荐任务粒度：

- 重写一篇小节；
- 核对一组相邻操作步骤；
- 补截一个完整流程的入口、填写态和结果页；
- 核实一条或多条相互关联的「待确认」。

### 2. 给 Agent 的任务模板

把下面内容复制给 Agent，替换尖括号中的内容：

```text
任务：核对并更新 <章节文件> 的 <小节编号与标题>。
目标：<要解决的内容或读者操作问题>。
范围：只修改 <允许修改的文件和小节>，其他章节不要动。
依据：以测试环境当前可操作的界面为准；旧手册和原型仅用于对照。
操作：需要补截 <入口 / 表单 / 结果等>；需要验证 <具体步骤或规则>。
测试数据：只能使用我新建的「手册示例-<名称>」；本任务 <允许 / 不允许> 提交审批。
禁止：遵守 README 和 _ref/环境现状-菜单与路由.md 的全部安全红线。
记录：无法验证的内容写入本章「待确认」，不要猜测；发现菜单或路由变化时先报告。
产出：正文、截图、变更说明、环境核对结果、未完成事项。
交付：先说明改了什么、截了哪些图、哪些步骤没有验证，不要直接提交或推送。
提交：提交前必须在 CHANGELOG.md 登记本次改动（修改内容、截图、验证范围、待确认、负责人），未登记不得提交。
```

如果任务只需要分析，请在开头明确写「只分析，不修改文件，不操作环境」。

### 3. 建分支

```bash
git switch main
git pull --ff-only
git switch -c ch06-6.10-调试流程
```

分支名使用「章-小节-改动」，例如 `ch03-3.2-数据表上传`。每位同事从最新 `main` 建自己的分支，不复用他人的任务分支。直接推送仓库需要协作者权限；没有权限时使用 fork + Pull Request。

### 4. 修改与留痕

- 菜单或路由有变化，先记录并告知负责人；确认后在 `_ref/环境现状-菜单与路由.md` 更新，再同步相关章节。
- 发现其他地方也受同一变化影响，在 PR 中列出，不顺带大改未认领的章节。
- 每完成一个小节就保存文件，并记录已核对步骤和截图位置，避免长任务中途丢失。
- 环境无法验证、权限不足或需他人审批的内容，写入本章「待确认」，不根据推测补全。
- **每次更新都要记录**：修改正文、截图、入口规则或编写规范时，在 [CHANGELOG.md](CHANGELOG.md) 中追加记录，与本次修改一起提交。新日期放在已有日期之前，同一天的修改追加到对应日期小节内，不能覆盖历史记录。记录修改内容、截图、验证范围、待确认事项和负责人，不能只写「更新手册」。
- 发生误操作时立即停止相关操作，保留页面状态与时间，如实告知负责人；不要尝试用更多写操作掩盖或修复。

### 5. 提交前验收

让 Agent 先自检，再由负责人复核：

- [ ] 只改了任务范围内的文件，没有覆盖其他人的修改。
- [ ] 菜单路径、按钮名称、字段和步骤与当前环境一致；界面原文与正文用词区分清楚。
- [ ] 没有为了补齐手册而虚构功能、点击结果或审批结论。
- [ ] 新增和替换的图片已放入 `images/`，引用路径正确，图片能打开且内容完整。
- [ ] 图号在本章连续，图注与图片内容对应，旧图和原型图已明确标注。
- [ ] 截图中的真实姓名、工号、手机号、密钥等已打码，没有暴露测试账号或口令。
- [ ] 本章「本章变更说明」与「待确认」已更新。
- [ ] `CHANGELOG.md` 已新增本次更新记录，包含修改内容、截图、验证范围和负责人。
- [ ] 已执行提交前 CHANGELOG 检查命令，确认 CHANGELOG 在本次改动中。
- [ ] PR 中列明验证范围、测试数据、未验证步骤和误操作（如有）。

可以用下面的命令检查文本改动：

```bash
git diff --check
```

再查看图片改动和最终差异：

```bash
git status --short
git diff --stat
```

`待确认汇总.md` 是各章末尾「待确认」的汇总，可以由维护人统一运行 `_ref/build_docx.py` 重新生成。`CHANGELOG.md` 不由脚本生成，每位负责人在每次更新时手工追加，避免历史记录被覆盖。

### 6. 提交 PR

提交前先确认 `CHANGELOG.md` 已登记本次改动（见「提交前必须检查 CHANGELOG」），再执行：

```bash
git add <本章文件> <本章新增或替换的图片> CHANGELOG.md
git commit -m "更新第6章6.10调试流程"
git push -u origin <你的分支名>
```

```bash
git diff --cached --name-only | grep -x 'CHANGELOG.md'
```

上面这条命令应在提交前执行，没有输出就说明漏了 CHANGELOG。

在 GitHub 创建 Pull Request，正文建议包含：

```markdown
## 修改范围
<章节、小节及对应问题>

## 环境核对
<实际走过的流程、核对日期；未验证的部分单独列出>

## 截图
<新增 / 替换图片及对应步骤>

## 待确认与影响
<需要产品或研发确认的事项，以及可能影响的其他章节>

## 测试数据与异常
<新建的「手册示例-」对象、提交到待审批的事项、误操作或无>

## CHANGELOG
<本次记录对应的日期与小节标题；确认为纯格式调整时说明原因>
```

PR 通过负责人复核后再合并。合并后由维护人更新汇总文件、重建站点或生成 Word。

## 三、并行协作建议

1. **按章认领，按小节交付**：第六章等较大章节可以多人分小节处理，每人单独建分支和 PR。
2. **公共事实集中维护**：菜单、路由和统一用词以 `_ref/环境现状-菜单与路由.md` 为准；发现冲突先确认，不在多个 PR 中各写一套。
3. **先合公共约定，再合章节**：涉及统一菜单改名、图号规则或公共参考文件的 PR 优先复核合并，其他分支随后同步 `main`。
4. **图片随正文同 PR**：不要只提交文字后另发一批难以对应的截图。
5. **环境和权限问题不互相猜测**：写入「待确认」，标明需要哪个角色或负责人核实。

如果修改同一文件产生冲突，保留双方已经核实的不同小节，再用当前环境核对冲突处；不要直接用「全部采用当前分支」或「全部采用传入分支」覆盖。

## 五、编写规范

### 结构

- 沿用 v3.4 的章节结构与编号（参考 `_ref/v3.4-chapters/`），在原位置更新；新功能插入对应章节，按顺序续编小节号。
- 小节写法：目标 → 入口（菜单路径）→ 操作步骤（编号）→ 说明 / 注意事项，配必要截图。
- 每个章节文件末尾保留：
  - `## 本章变更说明（v3.4 → v4.0）`：保留本次 v4.0 重写的历史说明，记录新增、修改、删除和未变的小节。
  - `## 待确认`：无法验证、权限不足、需要审批或产品确认的事项。
- 各章的 v4.0 编写说明不代替后续更新记录；此后的每次修改统一登记到 [CHANGELOG.md](CHANGELOG.md)。
- 附录 B 只更新有变化的 Logic 节点；未变化节点保留 v3.4 原文原图并明确标注。

### 状态标签

- 环境已上线：去掉旧版【规划】【待升级】【待上线】标签，按环境实际写。
- 1130 版本功能：小节标题加【1130 版本】，使用原型截图，图注写「（原型示意，以上线版本为准）」。
- 环境和原型都没有：保留 v3.4 原文与原标签，不删除。
- 旧版界面截图必须标明沿用日期和原因，例如「沿用 2026-11-06 旧版界面示意」。

### 截图

- 存放：`images/`，命名 `chNN-序号-简述.png`，例如 `ch02-03-部门成员配置.png`；原型截图加 `-proto`。
- 引用：`![图注](images/<文件名>.png)`，图下一行写「图 N-M 图注」。
- 关键操作覆盖入口页、弹窗或表单填写态、结果页；截图中应能看清对应按钮、字段和状态。
- 旧手册界面已变化的必须重截；当前环境可访问的旧图也按现行界面重截，确实不能访问时再保留并标注。

### 测试数据与文风

- 新建的数据统一加前缀「手册示例-」，不修改、不删除他人已有数据。
- 中文、业务语言、简洁；避免「不是……而是……」句式和机械排比。
- 菜单路径使用当前名称，例如 `资源 > 文档`、`本体建模 > 自动建模`。
- 全书统一用「部门」，不用「空间」；界面原文「个人空间」「默认企业空间」「全部有权空间」保留。
- 产品对外材料遵循目标项目的客户、版本和脱敏要求，详见项目 AGENTS.md。

## 六、本地预览与发布

### 阅读与校对

在 GitHub 页面打开章节即可阅读文字和图片。克隆完整仓库后，也可以用 VS Code、Typora 等支持相对路径图片的 Markdown 工具预览。

只复制一个 `.md` 文件而不带 `images/` 会导致图片无法显示；请保留目录结构。

### 生成本地站点

需要本机安装 pandoc，在仓库根目录执行：

```bash
python3 -I _ref/build_site.py
python3 -m http.server 8768
```

打开 http://localhost:8768/_site/ 浏览带导航的站点，图片可以放大查看。`_site/` 是生成目录，不提交。

### 生成 Word

```bash
python3 -I _ref/build_docx.py
```

需要 pandoc 与 Pillow，并将 v3.4 模板 `赛豆企业知识平台产品使用手册（v3.4）.docx` 放在本仓库上一级目录。模板体积大，不纳入仓库；脚本输出到上一级目录，并重新生成「待确认汇总」，不会改写 `CHANGELOG.md`。
